    How GRACE-Mem builds an answer

    Retrieval and answering+
    1. Analyze the question

      Extract keywords and embed the full question and individual keywords for complementary retrieval signals.

    2. Find and expand graph candidates

      Combine dense and BM25 entity search with keyword-level relation retrieval. Expand connected evidence with query-conditioned spreading activation.

    3. Rerank the graph and merge records

      Rank entity and relation candidates independently. Merge their linked compressed records with direct compressed-record retrieval, then deduplicate IDs.

    4. Select the compressed-record seeds

      Rerank the merged pool and retain the top-K records with provenance IDs. These records guide the corpus search.

    5. Inspect the original dialogue

      Use GREP for lexical search, READ for local dialogue, and VEC for semantic search. FINAL submits the selected provenance IDs within a bounded call budget.

    6. Validate, reconstruct, and answer

      Check submitted IDs against the search trajectory. Eligible coverage checks may restore omitted seeds; rebuild the selected raw spans as context for the answer model.

    Memory ingestion and updates+
    1. Preserve the dialogue and its origin

      Keep the raw text, dialogue timestamp, session ID, and message ID so selected records can be traced back to their source.

    2. Build complementary memory views

      Compress each dialogue unit with LLMLingua-2 and extract its entities. Resolve entity candidates through lexical and semantic matching with ADD or UPDATE decisions.

    3. Link relations to reconciled entities

      Extract entities before relations. Before writing a relation, replace its endpoints with resolved entity IDs.

    4. Write the graph and vector indexes

      Store entities, relations, compressed records, and provenance. Maintain separate entity, relation, and compressed-record vector indexes alongside the memory graph.

    Evidence validation and fallback+
    • Only admit verified additions

      Seeds can be kept directly. A new provenance ID is accepted only if a corpus-access tool observed it during the current search trajectory.

    • Restore omitted seeds when eligible

      For configured question categories, and only when capacity remains, an answer-blind check may add back useful omitted seeds. It does not remove retained evidence or launch a new open-ended search.

    • Preserve the complete seed context on failure

      If FINAL is missing, invalid, or empty, or ID validation leaves nothing, return the upstream compressed seed context unchanged. At the call cap, request FINAL without further corpus access.

    Reported defaults · 2 graph hops · top-16 seeds · 10 evidence-access calls · up to 16 final IDs

    Research manuscript: §3.1–3.4, Figures 1–2, Algorithm 1; defaults from Table 9 (p. 14).

    Explore implementation+
    • Separated graph discovery, compressed-record reranking, and provenance-linked raw-dialogue reconstruction; failed curation preserves the complete compressed seed context.
